# Design: Intelligent Post-Processing for asearch

Generated by /office-hours on 2026-06-07
Branch: main
Repo: izzzzzi/agent-asearch
Status: APPROVED
Mode: Builder

## Problem Statement

Currently asearch returns flat search results (`{title, url, snippet, date, score, raw_meta}`). 
An agent consuming these results must do all synthesis, cross-referencing, and enrichment 
manually — find the same project on GitHub + HN + Twitter, extract dates, resolve authors, 
build timelines. This is wasteful (tokens, API calls, latency) and inconsistent.

Level 1 (RawMeta) is already shipped. This plan covers Level 2 (multi-query search) and 
Level 3 (agent synthesis).

## What Makes This Cool

A single `asearch open --query "tool X by author Y" --synth` returns not just links but a 
structured report: "tool X has 3.4k stars on GitHub, was discussed on HN 2 days ago with 
120 points, author Y is @handle on Twitter with 5k followers — here's the timeline of 
releases." One command, complete picture.

## Constraints

- Must work without API keys (HN, GitHub, Reddit work zero-config)
- RawMeta already populated (Level 1 done)
- CLI output remains JSON for agent consumption
- Go binary — no Python/Node dependency
- Async by design — fetching + processing should not block each other

## Premises

1. **Multi-query search is useful** — searching "tool X" and "author Y" independently and 
   merging results gives more signal than searching "tool X Y" once.
2. **Post-processing via agent adds value** — LLM synthesis is better than heuristic merging
   for understanding relationships between results.
3. **Result dedup should be semantic, not just URL-based** — same project on HN vs GitHub 
   should be merged even with different URLs.
4. **The user already has an LLM** (Claude, Codex) — asearch should feed structured data to 
   it, not replace it.

## Approaches Considered

### Approach A: Built-in Synthesis (`--synthesize` flag)

Add `asearch open --query "..." --synth` that:
1. Runs normal search across all sources
2. Passes results (with RawMeta) to a configurable LLM endpoint (OpenAI-compatible)
3. Returns a synthesized JSON report alongside raw results

**Effort:** M (human: 2-3 days / CC: ~2h)
**Risk:** Low — additive feature, no breaking changes
**Pros:**
- Single command, complete workflow
- LLM configurable (any OpenAI-compatible API)
- Reuses existing search pipeline
**Cons:**
- Adds dependency on external LLM (latency, cost, API key)
- LLM prompt tuning needed per use case

### Approach B: Enhanced CLI with cross-ref hints

Add a lightweight cross-reference step in Go:
1. Parse query for tool name + author name patterns (heuristic)
2. Fire N parallel sub-queries ("tool", "author", "tool author")
3. Deduplicate results by normalized title/author match (not just URL)
4. Merge RawMeta across matched results
5. Add `related_to` field linking matched results

**Effort:** S (human: 1-2 days / CC: ~45min)
**Risk:** Very low — heuristics can always be refined
**Pros:**
- No LLM dependency, faster, cheaper
- Works offline
- Still compatible with agent post-processing
**Cons:**
- Less flexible than LLM synthesis
- Heuristic matching will miss some connections

### Approach C: Two-phase — Go cross-ref + CLI agent command

Phase 1 (Go): Add `--cross-ref` flag that runs multi-query heuristic matching (Approach B).
Phase 2 (CLI): Add `asearch synth` command that pipes results through any LLM.

**Effort:** M-L (human: 3-4 days / CC: ~3h)
**Risk:** Medium — more moving parts
**Pros:**
- Best of both: heuristic is fast, LLM is flexible
- Can use `--cross-ref` standalone without LLM
- `asearch synth` is optional enhancement
**Cons:**
- Two features to maintain
- More CLI surface area

## Recommended Approach

**Approach C** — two-phase: Go-level cross-ref first, then optional CLI synthesis.

Phase 1 (immediately useful, no LLM needed):
- Add `--cross-ref` flag to `asearch open`
- Parse query for known patterns ("by", "from", quotes)
- Fire sub-queries, merge results by normalized entity

Phase 2 (optional, LLM-dependent):
- Add `asearch synth` command
- Pipe current session results through configurable LLM
- Return structured report with cross-source connections

## Open Questions

1. LLM endpoint config — env var `ASEARCH_LLM_ENDPOINT`? Or `asearch config set llm ...`?
2. Should synthesis be streaming or block until complete?
3. Cross-ref heuristic: how aggressive? (match by author name? by project name substring?)

## Success Criteria

- `asearch open --query "claude code cli" --cross-ref` returns GitHub + HN results matched
  (same project, different platforms)
- `asearch synth -s SID` produces a JSON report with cross-source connections
- Zero false positives in heuristic matching (conservative by default)
